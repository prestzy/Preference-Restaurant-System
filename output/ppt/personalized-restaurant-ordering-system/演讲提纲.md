# 演讲提纲

## 汇报基本信息

- 汇报标题：Personalized Restaurant Ordering System
- 材料状态：有完整毕业设计报告、源代码、系统截图与测试证据
- 汇报场景：Final Year Project degree presentation and live demonstration
- 听众画像：2 位 Final Year Project supervisors，关注问题定义、技术合理性、系统完成度、实验可信度与局限
- 汇报时长：16–18 分钟，其中讲述约 13–14 分钟，现场演示约 3–4 分钟
- 总页数：13 页
- 证据密度：学术高证据；关键数字必须可追溯到报告或仓库证据

## 一句话主线

本项目为小型餐厅构建了一个轻量、可解释、手机优先的点餐系统，并证明基于食材、共点餐与混合评分的推荐能够在受控原型测试中响应顾客偏好和订单行为。

## 听众问题链

1. 小型餐厅为什么需要这种系统，现有流程有什么缺口？
2. 系统如何在不使用重型机器学习的情况下生成个性化推荐？
3. 推荐结果如何解释、验证并与真实点餐流程结合？
4. 测试结果能支持哪些结论，哪些结论仍受数据规模限制？

## 页序安排

### 第01页 — Personalized Restaurant Ordering System
- 页面任务：建立项目名称、研究定位和移动端使用场景。
- 这一页要讲：系统面向单餐厅 QR 点餐，用 Rust 实现可解释推荐；介绍本人、学号与导师。
- 过渡到下一页：先说明为什么这个问题值得解决。
- 需要准备：开场控制在 40 秒内。

### 第02页 — Problem and Research Gap
- 页面任务：界定成本、选择负担和推荐透明度三项问题。
- 这一页要讲：每桌部署设备成本高；菜单选择多但缺乏个性化；复杂模型不适合小型餐厅解释和维护。
- 过渡到下一页：这些问题形成三项研究问题。
- 需要准备：避免把原型夸大为商业级系统。

### 第03页 — Research Questions and Objectives
- 页面任务：锁定 RQ1、RQ2、RQ3 与对应目标。
- 这一页要讲：食材偏好如何改变排序、共点餐证据如何改变排序、哪种方法更能恢复隐藏目标菜品。
- 过渡到下一页：展示系统如何让顾客产生这些输入与行为数据。
- 需要准备：研究问题表述与报告保持一致。

### 第04页 — Proposed System and User Journey
- 页面任务：说明从 QR 进入到下单、状态更新与新行为数据回流的闭环。
- 这一页要讲：注册、浏览、选择偏好、查看解释、加入购物车、结账、后台处理。
- 过渡到下一页：该闭环由轻量模块化架构支撑。
- 需要准备：指出客户与管理员两个角色。

### 第05页 — Lightweight Web Architecture
- 页面任务：证明系统实现符合低耦合、高内聚和轻量部署目标。
- 这一页要讲：手机/后台浏览器、Rust Axum、推荐/搜索/订单/持久化模块、CSV/JSONL/本地图像。
- 过渡到下一页：聚焦推荐模块内部如何工作。
- 需要准备：解释为什么没有采用重型 ML 框架。

### 第06页 — Recommendation Processing Pipeline
- 页面任务：讲清硬过滤、内容评分、共点餐评分、混合与重排顺序。
- 这一页要讲：先排除不喜欢食材，再计算内容和共点餐证据，按数据可用性调整权重，最后做多样性重排。
- 过渡到下一页：分数之外，系统还要告诉用户“为什么”。
- 需要准备：区分过滤与评分。

### 第07页 — Explainability and Evidence Confidence
- 页面任务：说明推荐理由如何从匹配证据构建，而不是生成空泛文案。
- 这一页要讲：匹配喜欢食材、偏好标签、选中菜品的共点餐影响、排除项与证据置信度。
- 过渡到下一页：这些机制已经落实为可操作的系统功能。
- 需要准备：展示一条实际解释句。

### 第08页 — Implemented System Outcomes
- 页面任务：概览客户侧与管理侧完成度。
- 这一页要讲：移动菜单、搜索定位、偏好、推荐、购物车、订单状态、后台管理、历史订单与推荐测试器。
- 过渡到下一页：随后用测试证据验证实现质量。
- 需要准备：只讲已实现功能。

### 第09页 — System Testing Results
- 页面任务：展示自动化与报告级验证结果。
- 这一页要讲：115 项 Rust 测试通过；55 项报告级检查通过；覆盖数据、搜索、推荐、购物车、订单和持久化。
- 过渡到下一页：功能正确之后，再回答推荐是否会按预期改变。
- 需要准备：说明通过率不能代表生产环境可靠性。

### 第10页 — RQ1 and RQ2: Preference and Co-Order Impact
- 页面任务：用具体排名变化回答前两项研究问题。
- 这一页要讲：D14 由第 10 升到第 1；D30 因不喜欢 banana 被排除；D07 在新增共点餐证据后由第 7 升到第 1。
- 过渡到下一页：最后比较三种推荐方法的隐藏菜品恢复能力。
- 需要准备：强调这些是受控测试。

### 第11页 — RQ3: Recommendation Method Comparison
- 页面任务：比较 ingredient-only、co-order-only、fixed hybrid 的 Hit@3。
- 这一页要讲：5 个隐藏菜品案例中，ingredient-only 为 20%，co-order-only 与 fixed hybrid 均为 100%；平均排名分别为 14.20、1.80、1.80。
- 过渡到下一页：结果支持混合方向，但也暴露样本与设定限制。
- 需要准备：明确固定偏好为 rice + chicken，不能声称统计普适性。

### 第12页 — Contributions, Limitations and Future Work
- 页面任务：平衡总结技术贡献、研究边界与下一步。
- 这一页要讲：贡献是轻量闭环与可解释混合推荐；限制是单餐厅、小数据、受控样本和原型持久化；未来可做真实用户研究、数据库与在线评估。
- 过渡到下一页：用一句话收束并进入演示。
- 需要准备：主动承认局限。

### 第13页 — Conclusion and Live Demo
- 页面任务：收束核心结论并给出演示路线。
- 这一页要讲：系统把偏好、历史行为与解释整合进可运行的手机点餐流程；演示客户点餐、推荐理由、订单状态与后台更新。
- 过渡到下一页：进入 live demo / Q&A。
- 需要准备：预置数据与备用截图。

## 可能被问到的问题

- 问题 1：为什么 ingredient-only 的 Hit@3 只有 20%？
- 回答思路：五个案例使用同一 rice + chicken 偏好，内容信号与隐藏目标不一定一致；这恰好显示单一内容信号的局限，也说明实验是受控原型比较而非普适结论。

- 问题 2：为什么 co-order-only 和 fixed hybrid 的结果相同？
- 回答思路：在保留的 60 条历史订单中，共点餐信号对这五个隐藏目标很强，0.6 的协同权重主导了 fixed hybrid；未来需扩大案例并做显著性与消融分析。

- 问题 3：新顾客没有订单历史怎么办？
- 回答思路：系统可以使用食材、标签和流行度信号；随着用户选择菜品和新增订单，协同证据逐步加入。

- 问题 4：为什么使用 CSV 而不是数据库？
- 回答思路：CSV 符合 FYP 原型的轻量和可审计目标，并便于演示算法输入；生产化将迁移到数据库并增加事务、并发和权限控制。
